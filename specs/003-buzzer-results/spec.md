# Feature Specification: 003 搶答與結果判定

**Feature Branch**: `codex-003-buzzer-results`

**Created**: 2026-11-11

**Status**: Draft

**Input**: User description: "功能：搶答與結果判定。搶答開始後，學生以組別為單位對每題送出答案。每組每題只有一筆有效答案，送出後鎖定。每題以系統收到時間最早的組別為搶答成功，不判斷對錯。搶答結束前學生看不到其他組別的作答狀況；老師可即時檢視各題作答狀況。結束後學生可檢視每題的成功組別、答案與自己組的結果。邊界情況：階段不對時送出、空白答案、同組多人同時送出、兩組幾乎同時送出、重複送出。"

## Clarifications

### Session 2026-11-11

- Q: 搶答進行中，老師的即時畫面應顯示哪些組別作答資料？ → A: 各組提交狀態、有效答案及目前成功組別。
- Q: 活動結束後，學生應能看到哪些組別的答案？ → A: 成功組別的答案與自己組的答案／結果；不顯示其他組答案。
- Q: 正常本機連線下，老師應在答案送出後幾秒內看到作答狀況更新？ → A: 2 秒內。
- Q: 若兩組有效答案的伺服器接收時間戳完全相同，應如何決定該題成功組別？ → A: 按伺服器確認有效提交的先後，決定唯一成功組別。
- Q: 要以多少名學生同時連線作為 2 秒即時更新的驗收目標？ → A: 以實際班級人數驗收。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 學生送出並鎖定各題答案 (Priority: P1)

搶答開始後，學生代表所屬組別，針對活動題目提交答案。每組每題只接受一筆有效答案；收到後該組該題即鎖定。每題最先送達系統的有效答案所屬組別成為搶答成功組別，系統不判斷答案正誤。

**Why this priority**: 每題唯一且公平的成功結果是老師檢視作答情況與學生查看活動結果的基礎。

**Independent Test**: 建立一個含多題與多組的活動，讓不同組別依序及同時提交答案；確認每組每題最多一筆答案，且每題成功組別由系統收到有效答案的先後決定。

**Acceptance Scenarios**:

1. **Given** 活動已進入「搶答中」、學生已選定有效組別且選擇活動題目，**When** 學生提交非空答案，**Then** 系統接受該組該題的第一筆答案並回報已鎖定。
2. **Given** 學生提交的答案只有空白字元，**When** 系統驗證答案，**Then** 系統拒絕該答案、不鎖定該組該題，並提示學生輸入答案。
3. **Given** 活動尚在「準備中」或已「結束」，**When** 學生提交答案，**Then** 系統拒絕操作且不新增或改變任何作答結果。
4. **Given** 同組兩位學生同時替同一題提交有效答案，**When** 系統處理兩筆提交，**Then** 只有第一筆有效答案被接受，其餘提交收到已鎖定提示，且已接受答案不被覆蓋。
5. **Given** 同一組已成功提交某題答案，**When** 該組任一學生再次提交相同或不同答案，**Then** 系統拒絕重複提交並保留第一筆答案。
6. **Given** 不同組別幾乎同時提交同一題的有效答案，**When** 系統收到兩筆提交，**Then** 收到時間較早的組別成為成功組別；若時間精度相同，依系統確認有效提交的先後決定，且不採用用戶端提供的時間。
7. **Given** 提交包含未知題號或沒有有效組別身分，**When** 系統驗證提交，**Then** 系統拒絕操作且不建立作答或成功結果。

---

### User Story 2 - 老師即時檢視各題作答狀況 (Priority: P1)

活動搶答期間，老師可按題目檢視各組是否已提交、各組有效答案，以及目前最先成功的組別與答案。學生只能看到自己組別的提交確認，不能得知其他組別的提交狀況或答案。

**Why this priority**: 老師需要掌握活動進度並確認每題的搶答情況；限制學生可見資料則維持搶答公平。

**Independent Test**: 讓多組學生提交不同題目的答案，同時檢查老師畫面會更新所有組別狀態，而學生畫面及其收到的活動更新只包含本組資訊。

**Acceptance Scenarios**:

1. **Given** 老師已登入且活動正在「搶答中」，**When** 任一組提交有效答案，**Then** 老師可即時看到該題的組別提交狀態、答案及目前成功組別。
2. **Given** 多題、多組已有作答或尚未作答，**When** 老師檢視作答狀況，**Then** 系統按題目顯示每組「已提交」或「尚未提交」，並僅對已接受的答案顯示作答文字。
3. **Given** 活動仍在「搶答中」，**When** 學生檢視畫面或接收活動更新，**Then** 學生只能得知本組的答案是否已接受及鎖定，不得取得其他組別的作答狀態、答案或成功資訊。

---

### User Story 3 - 活動結束後檢視每題結果 (Priority: P1)

活動結束後，學生可檢視每題最先成功的組別及其答案，也可檢視自己組別該題的答案、是否成功，以及未作答狀態。老師可檢視各組完整作答情況。系統只判定先後，不評斷答案正確性或計分。

**Why this priority**: 活動結束後，師生需要確認每題的搶答結果及各組參與情況。

**Independent Test**: 先讓多組對多題提交答案，再結束活動；確認學生能看到各題成功組別、成功答案與本組結果，且老師能看到完整作答情況。

**Acceptance Scenarios**:

1. **Given** 活動已「結束」，**When** 學生檢視結果，**Then** 每題顯示成功組別與其答案，以及該學生所屬組別的答案和成功／未成功／未作答狀態。
2. **Given** 活動已「結束」，**When** 學生檢視結果，**Then** 系統不顯示其他非成功組別的答案。
3. **Given** 老師已登入且活動已「結束」，**When** 老師檢視結果，**Then** 系統顯示每題所有組別的提交狀態與已接受答案，並標示成功組別及答案。
4. **Given** 學生於同一次仍在執行的活動中重新連線，**When** 系統恢復其既有組別與活動階段，**Then** 學生看到與目前階段相符且伺服器已接受的本組作答鎖定狀態；活動結束後則看到已公布結果。

### Edge Cases

- 活動階段不是「搶答中」時，所有答案提交都拒絕且不改變結果。
- 空字串或只含空白的答案不算有效提交，不占用該組該題的唯一提交名額。
- 同組多人同時提交同一題時，只接受一筆；其餘不得覆蓋已接受答案。
- 同組重複提交相同或不同答案時，第一次有效答案維持鎖定。
- 不同組別幾乎同時提交時，以系統收到有效答案的先後決定成功組別；時間精度相同則採系統確認有效提交的先後。
- 無效答案、未知題號、未加入有效組別或錯誤階段的提交，不得影響搶答成功順位。
- 尚未匯入題目或題號不屬於目前活動時，不建立答案或結果。
- 搶答中學生端不得從初始資料、即時更新、錯誤訊息或結果查詢取得其他組別資料。
- 活動結束後，學生可看成功答案及本組結果，但不能看其他非成功組別的答案；老師可檢視完整結果。
- 活動進行中成員離線或重新連線，不得解除已接受答案的鎖定或變更所屬組別。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 沿用目前活動已驗證的老師、學生及組別身分；答案提交 MUST 以該學生目前所屬有效組別為準，不接受用戶端另行指定組別。
- **FR-002**: 系統 MUST 只接受目前活動題目清單中的題目答案；若活動尚無題目或提交未知題號，MUST 拒絕提交且不得改變結果。
- **FR-003**: 系統 MUST 只在活動處於「搶答中」時接受學生提交答案；準備中及已結束階段的提交 MUST 被拒絕且不改變結果。
- **FR-004**: 有效答案 MUST 至少包含一個非空白字元；空白答案 MUST 被拒絕且不鎖定該組該題。系統 MUST 保留有效答案的原始文字內容。
- **FR-005**: 每個組別對每個題目 MUST 最多只有一筆被接受的答案；同組任一學生成功提交後，該組該題 MUST 立即鎖定。
- **FR-006**: 系統 MUST 拒絕已鎖定組別對同一題的任何後續提交，不論內容是否與第一筆答案相同；第一筆已接受答案及結果 MUST 保持不變。
- **FR-007**: 多位同組學生同時提交同一題時，系統 MUST 僅接受其中第一筆有效提交，其餘 MUST 明確收到已鎖定結果，且不得覆寫第一筆答案。
- **FR-008**: 對每一題，系統 MUST 將最先收到的有效答案所屬組別標示為搶答成功組別；無效答案及被拒絕的重複提交 MUST 不參與先後判定。
- **FR-009**: 搶答順位 MUST 依系統收到提交的時間判定，不得依用戶端提供的時間或成功宣告判定。若兩筆有效答案的系統接收時間精度相同，MUST 依系統確認其有效的先後順序決定唯一成功組別。
- **FR-010**: 本功能 MUST 只判定提交是否被接受及各題搶答先後；MUST NOT 判斷答案正確性、提供正確答案或依答案計分。
- **FR-011**: 活動尚未結束時，學生 MUST 僅能取得自己組別的提交接受／拒絕與鎖定狀態；學生 MUST NOT 取得任何其他組別的提交狀態、答案或搶答成功資訊。
- **FR-012**: 活動處於「搶答中」時，已登入老師 MUST 能按題目即時檢視所有有效組別的提交狀態、已接受答案，以及目前成功組別與答案。
- **FR-013**: 系統 MUST 以清楚訊息說明錯誤階段、空白答案、未知題號及已鎖定等拒絕原因；被拒絕的提交 MUST NOT 改變已接受答案、組別鎖定狀態或搶答結果。
- **FR-014**: 活動「結束」後，學生 MUST 能檢視每題成功組別與成功答案，以及自己組別的答案、成功／未成功／未作答結果。
- **FR-015**: 學生查看結束結果時 MUST NOT 取得其他非成功組別的答案；已登入老師 MUST 能檢視每題所有組別的提交狀態與已接受答案。
- **FR-016**: 同一次活動仍有效期間，學生離線或重新連線 MUST NOT 清除或解除伺服器已接受的組別答案及鎖定狀態；系統回傳資料 MUST 按目前角色與活動階段限制可見內容。
- **FR-017**: 系統 MUST 不接受用戶端指定搶答時間、勝出組別、其他組別答案或是否正確等資料作為權威結果；顯示的作答狀況與結果須以活動中已接受的提交為準。
- **FR-018**: 本功能 MUST 使用既有活動階段與組別設定，並依賴功能 002 提供的目前活動題號；不得在本功能中新增題目敘述、答案正確性設定或多填空模式。

### Key Entities *(include if feature involves data)*

- **活動題目**：目前活動所使用的唯一題號；由活動已匯入的題目清單識別。
- **組別作答**：一個組別對一個活動題目所提交的第一筆有效答案，以及系統確認該答案的先後資訊與鎖定狀態。
- **搶答成功結果**：每題最先提交有效答案的組別與該筆答案；系統不包含答案正確性判斷。
- **組別活動結果**：每題該組已提交答案、是否為成功組別，或尚未作答的狀態。
- **作答狀況**：老師可檢視的每題各組提交狀態、已接受答案及目前搶答成功結果。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 驗收案例中，每組每題最多只有一筆有效答案；第一筆有效答案被接受後，重複或並行提交均不會改變該答案。
- **SC-002**: 100% 多組同題競答案例中，系統都標示最早收到的有效答案組別為成功組別；接收時間相同時，結果依系統確認有效的先後而唯一決定。
- **SC-003**: 100% 非「搶答中」階段、空白答案、未知題號、無有效組別或已鎖定提交案例均被拒絕，且拒絕前後既有作答及搶答結果完全一致。
- **SC-004**: 正常本機連線且一位老師與本班全體學生同時連線時，老師於有效答案送出後 2 秒內可在作答狀況中看到該題更新；更新包含組別狀態、已接受答案及目前成功結果。驗收人數以實際班級人數為準，不另設產品人數上限。
- **SC-005**: 搶答尚未結束時，學生端收到的每個畫面與活動更新中，其他組別的答案及作答狀態曝光數為 0。
- **SC-006**: 活動結束後，100% 學生結果檢視案例都能正確辨識各題成功組別與答案，以及本組成功、未成功或未作答狀態；老師亦能檢視完整組別作答狀況。
- **SC-007**: 在情境驗收中，學生能明確辨識答案已接受並鎖定或提交被拒絕，老師能按題目判讀各組作答進度與成功結果，無須判斷答案正確性。

## Assumptions

- 本功能沿用 001 的老師／學生角色、有效組別、三個活動階段及重新連線組別恢復行為；答案只可在「搶答中」提交。
- 本功能沿用 002 匯入並關聯至目前活動的題號清單；題目敘述與標準答案不屬於本功能資料。
- 空白判斷會忽略答案字串前後及其中的空白字元；只要含非空白字元即為有效內容，接受後保留原始文字，不自動修剪答案。
- 第一筆有效提交即鎖定本組本題；本活動中不提供修改、撤回或老師重置單一答案的操作。
- 同一組多位學生的首筆有效提交代表整組答案；系統收到有效提交的先後是唯一搶答依據，完全同時時以系統確認提交的先後決定。
- 學生活動結束後只能看到每題成功答案與本組結果；其他非成功組別的答案仍只供老師檢視，以降低不必要的答案揭露。
- 作答結果隸屬目前執行中的單一本機活動；伺服器程序重啟後是否保存或還原活動資料不屬於本功能範圍。
- 老師需使用 001 已有的老師權限檢視全組即時及結束結果；本功能不新增其他角色或答案評分流程。
