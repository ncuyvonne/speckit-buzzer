# Worksheet Group Layout Contract

## Header and question rows

Feature 004 extends Feature 002's selected Google worksheet format:

- Before parsing or replacing the active question layout for a new activity, call `spreadsheets.developerMetadata.search` for `metadataKey=sb004` and `visibility=PROJECT`. Reject only if a returned record is row/column metadata on the selected numeric `sheetId`; explain that export replaced placeholders and anchors preserve the old activity's re-export mapping, then direct the teacher to the original template or a copy made from that template. Leave the current worksheet and questions unchanged. Ignore other metadata keys, other tabs, and non-row/column locations. This check also applies after an activity reset or backend restart, when the in-memory export manifest is gone but sheet anchors remain. Do not offer a reset that removes these anchors, because that would destroy mapping evidence for the already-exported activity.
- PROJECT metadata is visible only to its creating Google Cloud project. Keep the backend's configured credentials in that project across activity resets and restarts so this import guard can find the anchors.

- Find one unique header row containing exactly one `題號` and one `作答` title, after trimming surrounding whitespace. The row and columns are discovered from the current worksheet; no fixed coordinate is assumed.
- Preserve displayed, non-empty question IDs in source order. IDs must be unique. Count up to 100 top-level question IDs; group child rows do not increase that count.
- A question-number row with no recognized placeholder is a single question with one answer slot.
- A grouped question starts on a row with a non-empty question ID and answer cell exactly `（1）` or `(1)`. Every next child slot occupies the next row, has a blank question-number cell, and contains the next sequential marker by itself, using either marker style independently. A group may mix full-width and ASCII parentheses; mismatched delimiters and leading-zero numbers are invalid.
- A group contains 2–20 slots. Repeated, missing, reversed, non-starting, orphaned, or non-contiguous markers make the import invalid. Rows with no question ID and no marker remain ignored as in Feature 002.
- The shortest supported group submission, with `a` in every slot, must fit the limit in the [WebSocket contract](./group-questions-websocket.md). This also checks the encoded length of displayed question IDs.
- Each invalid import fails as a whole and leaves the previously imported activity worksheet and question definitions unchanged. Error details identify the question/row and how to correct it.

## First export

1. Require an authenticated teacher, an ended activity, an imported worksheet and a `READY` winning-results snapshot. `UNAVAILABLE` aborts without writing. If `READY` contains no winner for a single question, clear its target cell; if it contains no winner for a group, preserve all original marker cells and omit them from the write batch.
2. Read the currently selected sheet and find unique live headers and question-ID rows. Map each group slot by its current full-width or ASCII-parenthesis marker and verify each question's kind and exact slot sequence against the imported definition. If any target is ambiguous, abort before writing.
3. Prepare the [manifest](../data-model.md#exportmanifest) with the original target coordinates, raw previous cell values, intended values and positive metadata IDs. Use one ID per distinct target row, the header row and each of the two relevant columns. Use PROJECT visibility, stable application key `sb004`, and a compact attempt token to identify the records. Keep the expected key, token, ID, sheet and location for validation. Preserve the manifest before dispatch.
4. Use one `spreadsheets.batchUpdate` with applicable per-target `UpdateCellsRequest` entries and the first-export `CreateDeveloperMetadataRequest` entries. Winning answer cells receive literal `stringValue` entries, including answers beginning with `=`. Clear a no-winner single target using an exact target range with the `userEnteredValue` mask and no value. Do not send a cell request for no-winner group slots: their original placeholder text stays in place. Other cell values, formulas, notes and formats remain intact. PROJECT dimension metadata is separate from cell data and carries only identifiers.
5. A definitive rejection leaves the entire batch unapplied. Acknowledged success stores the confirmed manifest. A new activity uses the original template or a copy made from that template; the system does not remove `sb004` anchors to reset an exported worksheet.

## Repeat export

1. Read the current sheet grid with `spreadsheets.get` and `includeGridData`, requesting both `formattedValue` and exact `userEnteredValue`; query row/column metadata separately with `spreadsheets.developerMetadata.search`. Use displayed values to identify the unique header, question IDs, and parenthesis markers in either style; preserve the raw prewrite value for first-attempt reconciliation; treat missing cells inside the resolved grid as blank. Missing anchor data is insufficient evidence.
2. Require all recorded metadata to match the exact original row/column, sheet and attempt. Require the same unique header and question-ID mapping, same blank-numbered child relationships, and the same original question/slot coordinates. Blank cells and matching offsets alone do not establish identity. Do not use confirmed target-cell values as identity evidence.
3. Missing, moved or inconsistent identity evidence aborts the whole export with an actionable layout error. The teacher sees which position or relation needs inspection where it can be identified. With matching evidence, write winning vectors and no-winner single clears to the original coordinates in one value-only batch; omit no-winner group slots so their original markers remain unchanged. A target-cell value edited after confirmed export is overwritten by the current activity result for winning answers or cleared singles; it does not by itself mean the original cell mapping changed. Do not recreate anchors on repeat.

## Uncertain results and external edits

- On a lost first-export response, compare the PREPARED manifest's exact anchors, live mapping and intended cell values with the latest read. A complete match confirms and promotes the manifest and reports success without sending a second batch. Allow a new first write only after definitive non-application under Feature 002, absence of the attempted anchors, and fresh marker validation. If the outcome is inconclusive or only partly matches, retain PREPARED and report `SHEET_WRITE_UNCONFIRMED` without writing again. Reconcile an outstanding first attempt before initiating a later write.
- On an uncertain confirmed repeat, retain the existing CONFIRMED activity manifest and keep the pending repeat's prewrite/intended values privately in `GuidedNotesService`. Revalidate the existing anchors and mapping before comparing target values. Promote the updated manifest when all targets match the pending intended values; clear the pending repeat after a matching prewrite read-back; otherwise keep it pending and do not issue another batch.
- Repeat exports use the confirmed manifest for read-back. Preserve the Feature 002 deadline and operation lock, including when the original API request is still pending. An unresolved reply never claims definite success or failure.
- Keep the sheet's structure stable from the final read through the batch. Sheets' atomic batch guarantees cover the submitted requests. A collaborator can edit between the read and write because Sheets provides no revision precondition for this operation.
